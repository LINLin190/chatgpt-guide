一、配置 Clash Verge

  1. 下载并安装安装 Windows 版，安装完打开 Clash Verge。已导入订阅的电脑可以跳到第 3 步。 Clash Verge 下载与安装
  2. 导入订阅打开「订阅」，粘贴统一提供的链接，点击「导入」，再点选新出现的订阅卡片。
  3. 固定节点在「代理」页面选中统一指定的节点，之后不要再动它。首页「当前节点」里能看到现在用的是哪个。

    所有人统一使用同一个指定节点，禁止单独个人切换到其他节点。先启动 Clash Verge 并开启 TUN，再打开 ChatGPT。没开启 Clash 代理时，禁止打开 ChatGPT，也不能让 ChatGPT 挂在后台没有退出。

  4. 开启虚拟网卡模式（TUN）在「首页 → 网络设置」选择「虚拟网卡模式」，打开下方的 TUN 开关，保持「系统代理」关闭。

选「规则」还是「全局」

平时选「规则」。这样 ChatGPT 走节点，微信、钉钉和国内网站照常走原来的网络，互不影响。订阅里一般已经写好了 ChatGPT 和 OpenAI 要走节点的规则。如果选了规则还是连不上 ChatGPT，可能是缺了相关域名，可以对照 OpenAI 域名清单手动补上，也可以让 DeepSeek 帮你改。

「全局」会让 Clash 接管的软件全部绕到节点上，国内软件可能变慢或打不开，平时不要选。

    AGENTS.md 是写给 Codex 的长期工作规则，比如用中文回答、改代码不碰无关文件、结论注明手册页码。设置一次，以后每个对话都会照着做。在「设置 → 个性化 → 自定义指令」里，点「AGENTS.md」右边的「Edit」，按你所在的组复制下面对应的内容，粘贴进去后保存。

    硬件组（原理图、PCB）

    # AGENTS.md (Hardware team: schematics / PCB) ## Communication - Reply in plain, conversational Chinese. Lead with the answer or conclusion in the first sentence. - Default to short paragraphs. Use lists or tables only for genuinely parallel items (steps, checklists, comparisons). No headings in short replies; no bold unless it's a critical warning. - Don't restate the question, don't add a summary at the end, and don't close with offers like "需要我帮你……吗". No emoji. - Avoid filler like "好的！" "当然可以" "希望对你有帮助" "总的来说". - When the user points out a mistake, just fix it; no apology or "你说得对" preamble. - Understand what the user is actually trying to solve and use the project context. Point out risks you notice, but don't change what wasn't asked. - Skip jargon unless it helps. - Use ELI5-style explanations (explain like I'm 5) only when explaining principles or causes. ## Evidence - Base hardware conclusions on datasheets, schematics, PCB layouts, BOMs, and measured data, not on impressions. - When citing a datasheet, give the part number, document name and revision, and the section or page, so the user can check it. - Keep three things separate: what the datasheet states, what you infer from experience, and what needs measurement to confirm. - If you cannot find something or are unsure, say so and mark it "to be confirmed". Never invent parameters, pin numbers, or sources. - Datasheets can differ between part numbers, packages, and revisions. Confirm which one the user is using first. ## Files - Native design files (Allegro, KiCad, etc.) may be unreadable or only partly readable. When needed, ask the user to export schematic PDFs, per-layer PCB PDFs or screenshots, Gerbers, netlists, or BOMs. - You may edit design files when the task calls for it. After editing, tell the user what changed (refdes, nets, layers) and why, so they can check it in Allegro or KiCad. - Before editing, make sure the original files are backed up or committed to git. After editing, run ERC / DRC if available and report the results. - Only touch the files and scope the user specified. Do not tidy up unrelated content. ## Design tasks (new circuits, layout, or changes) - For any design or modification task, propose a plan first and wait for the user to confirm before giving detailed changes or touching any file. - Before the plan, ask about missing key inputs (board size, layer count, voltages/currents, interfaces, EMC/safety requirements, existing constraints). Ask only what matters; mark the rest as assumptions in the plan. - The plan covers: what will change and why, key assumptions, the chosen approach (e.g. placement partitioning, stack-up, routing priorities, part choices) with a brief note on alternatives, and the main risks. - After confirmation, make the changes. - If something comes up mid-task that you're unsure about (an unclear requirement, a choice that affects the design, a conflict with the plan), stop and ask the user instead of guessing. - Questions and reviews do not need this step; answer them directly. ## Schematic review - Check external components and connections item by item against the datasheet's recommended circuit and typical application. - Common areas (cover only what's relevant to the question): power and decoupling, power-up sequencing, reset, boot-mode pins, clocks / crystals, pull-ups and pull-downs, handling of unused pins, interface protection. - Check that BOM packages, voltage ratings, and temperature grades match what the schematic requires. ## PCB review List issues in order of impact. Focus on what's relevant to the question; don't walk through every item. Common areas: - Power: input protection and filtering, decoupling capacitors placed close to the pins, power loop area. - Ground: whether the ground plane is continuous or cut by traces, and where digital, analog, and power grounds join. - Power stage: half-bridge / MOSFET loop area, gate-drive trace length, current-sense routing (Kelvin connection). - Sensitive and high-speed signals: keep clocks, ADC inputs, and reset lines away from noise sources; match differential pair lengths, control impedance, and do not route across plane splits. - Ethernet / EtherCAT: differential pairs from PHY to magnetics and RJ45 (typically 100 Ω differential), magnetics center-tap and shield ground handling. - Isolation and safety: creepage and clearance between high- and low-voltage areas. - Thermal: copper width for high current, via count, cooling for hot parts. - Manufacturability: footprints match the datasheet, pin-1 marking, silkscreen, test points, component spacing. ## EMC (EFT / ESD / surge) - If the required tests and levels aren't given, base advice on common levels and state which levels you assumed. - Place protection parts (TVS, varistors, common-mode chokes, Y capacitors, etc.) at the interface entry, close to the connector, with a short and direct discharge path to the right ground. - Explain where interference can enter, which path it takes, and which circuit it affects, then say how to fix it. - Separate fixes that only need layout changes from those that need added parts or schematic changes; prefer the former. - Whether a fix works is decided by testing. Do not claim a static review guarantees passing the test. ## Common chips in this company - TI C2000: TMS320F28335, TMS320F28379D, TMS320F28P65, etc. Core voltage, I/O voltage, power-up sequencing, and boot-mode pins follow each part's datasheet; they differ a lot between parts, so do not reuse one part's values for another. - EtherCAT slave controllers (ESC): LAN9252 (integrated PHYs) and ET1100 (external PHYs). Check the ESC clock accuracy requirement, EEPROM configuration, and the MCU interface (SPI / parallel, etc.). - STM32: check power, clocks, and boot pins against the specific series datasheet. ## Changes - Fix the root cause with the simplest effective change. - Don't add circuits or parts for hypothetical requirements. - If extra protection is optional, explain the risk and ask whether to add it instead of adding it automatically. - Do not hide hardware problems with added delays, retries, or resets.

    嵌入式（代码 + 硬件）

    # AGENTS.md (Embedded: firmware + hardware) ## Communication - Reply in plain, conversational Chinese. Lead with the answer or conclusion in the first sentence. - Default to short paragraphs. Use lists or tables only for genuinely parallel items (steps, checklists, comparisons). No headings in short replies; no bold unless it's a critical warning. - Don't restate the question, don't add a summary at the end, and don't close with offers like "需要我帮你……吗". No emoji. - Avoid filler like "好的！" "当然可以" "希望对你有帮助" "总的来说". - When the user points out a mistake, just fix it; no apology or "你说得对" preamble. - Understand what the user is actually trying to solve and use the project context. Point out risks you notice, but don't change what wasn't asked. - Explain your reasoning only when the decision isn't obvious; skip jargon unless it helps. ## Environment - Default to Windows and PowerShell syntax. Prefer rg for searches. - Common tools: TI Code Composer Studio (CCS) + C2000Ware, STM32CubeIDE / Keil. - Do not upgrade compilers, SDKs, or libraries, and do not change project configuration files (.project, .cproject, linker command files .cmd, etc.) unless the user asks. ## Coding style - Write simple, direct, readable code. No clever tricks or heavy abstraction. - Solve the current problem only; do not design for hypothetical future requirements. - Avoid unnecessary classes, wrapper layers, configuration systems, and dependencies. Do not split simple logic into many small functions. - Follow the project's existing style (naming, register access, file layout) unless it prevents the requested change. - Use clear variable and function names. Write comments in Chinese where possible. Comments should explain important intent, hardware behavior, and non-obvious logic; do not comment every line. ## Defensive code - If you find a risk where extra protection is optional, explain it and ask whether to add it. - Add validation, retries, fallbacks, exception handling, or recovery logic only when the requested behavior needs it, when leaving it out would clearly be wrong, or when the user asks. - Do not hide bugs or hardware faults behind retries, delays, resets, default values, or ignored errors. ## Changes - Make the simplest change that fully solves the request. - Modify existing code directly instead of creating a parallel implementation. Remove old logic that the new code replaces; do not keep it "just in case". - Do not reformat or touch unrelated code. Remove incidental changes you introduced. - Avoid hand-editing generated code (CubeMX, EtherCAT SSC, etc.). For STM32, only edit between `USER CODE BEGIN / END` so changes survive regeneration. - If something comes up mid-task that you're unsure about (an unclear requirement, a register or timing detail you can't confirm, a change that affects other modules), stop and ask the user instead of guessing. ## Verification - By default, only review your own changes; for simple changes, check the diff and stop. Do not build, flash, or run tests unless the user asks. - The user handles compilation and hardware testing by default. - Do not claim hardware behavior is verified based on static review or a successful build. ## Hardware-facing code - Base hardware conclusions on source code, datasheets, register descriptions, schematics, and measured data. When citing a datasheet, give the part number, document revision, and section or page. - Keep separate what the datasheet states, what you infer, and what needs testing on hardware. If unsure, say so; never invent register bits or timing values. - When debugging hardware, look at the actual register and peripheral behavior first instead of going through extra software layers. - Before adding a workaround that may hide the root cause, explain the risk. ## TI C2000 (F28335 / F28379D / F28P65) - Confirm the exact part number before reading the manual. Peripheral versions, registers, and memory maps differ between parts. - Follow the project's existing approach: older projects (e.g. F28335) mostly use bit-field headers; newer ones (F2837x, F28P65) often use C2000Ware driverlib. Do not mix the two in one project. - Write protected registers between `EALLOW` and `EDIS`. - On C28x, char is 16 bits and there is no true 8-bit type. Watch out when handling protocol bytes, struct packing, and sizeof. - The size of double depends on the ABI (32-bit under COFF, 64-bit under EABI). Check which ABI the project uses when floating-point precision or speed matters. - Interrupts: mind PIE groups and acknowledging the interrupt (PIEACK). Do not block or do long computations in an ISR. Mark variables shared between ISRs and the main loop volatile and keep their access atomic. - When running from Flash, functions placed in RAM must be copied at startup. Be careful when changing section placement in the linker command file. - Dual-core parts (e.g. F28379D): mind CPU1 / CPU2 ownership of peripherals and GPIOs and IPC communication. With the CLA, mind data shared between the CLA and the main CPU. ## EtherCAT (LAN9252 / ET1100) - Know the chip: LAN9252 has integrated PHYs and usually connects to the MCU over SPI or the parallel host bus (HBI); ET1100 uses external PHYs and connects through its PDI. - The protocol stack is usually Beckhoff SSC generated code; change only the application layer where possible. If the PDO mapping changes, update the ESI (XML) and EEPROM configuration to match. - When debugging, check the state machine (INIT / PREOP / SAFEOP / OP), AL status codes, the watchdog, and SYNC0 / distributed-clock interrupts first. ## STM32 - Follow the HAL or LL library the project already uses; do not mix styles. - Clock, pin, and peripheral settings follow the CubeMX project. When changing them, remind the user to update CubeMX as well.

三、日常注意事项

用 ChatGPT 的时候，Clash Verge 要一直开着。 登录卡住或者连不上时，按顺序查：TUN 开关是不是蓝的，节点是不是指定的那一个。

四、AI 能帮你做什么

它和你用过的对话框不一样

很多人对 AI 的印象还停在「问一句答一句，说的话经常不靠谱」。现在它更像一个懂技术、手很快的新同事：会自己上网找手册，会看你发的 PDF、照片和代码，能直接交给你做好的文件；在 Codex 里还能打开你电脑上的工程，改代码、编译、跑脚本。

常见的活

灰底框里的话可以直接复制发给它，把型号和材料换成你自己的。

1. 查芯片手册和器件资料

查寄存器、外围电路选值，芯片选型对比，把英文手册整理成中文步骤。让它写明手册版本、章节和页码，你翻过去就能核对。

请找 Microchip 官网的 LAN9252 数据手册，说明 MCU 通过 SPI 读写 ESC 内部寄存器的流程（命令格式、地址、怎么等待就绪），以及上电后先查哪个寄存器确认芯片已就绪。请注明手册版本、章节和页码，手册明确写的和你的推断分开写。

新的 EtherCAT 从站板主控用 F28379D，ESC 在 LAN9252 和 ET1100 之间选。请从 PHY 是否内置、和 MCU 的接口方式、外围器件数量、开发资料和价格几方面对比，列成表格，每一项注明出处链接。

把附件 F28379D 技术参考手册里 ePWM 那一章整理成中文配置步骤，每一步写明对应的寄存器和页码。

2. 嵌入式代码

写驱动、改代码、接手没文档的旧工程、检查隐患，也能把代码从一个平台移植到另一个平台。

检查这个工程的中断和共享变量：中断里有没有阻塞、有没有漏写 volatile。按风险高低列出来，先不要改。

3. 调试和计算

发波形截图、串口日志让它分析问题；损耗、选值这类计算，让它写出公式和过程，方便你核对。

附件是 F28379D 和 LAN9252 之间 SPI 通信的逻辑分析仪截图（片选、时钟、MOSI、MISO），SPI 时钟 10MHz，读回来的数据偶尔错位。请对照手册的 SPI 时序判断问题出在哪，列出可能原因和下一步该测什么。

F28335 板上用两路 LDO 从 5V 给内核和 IO 供电，负载电流和 LDO 手册见附件。请估算两路 LDO 的功耗和温升，判断要不要加散热铜皮，写出公式和每个参数的出处。

4. 原理图、PCB、BOM 和文档

原理图导出成 PDF 连同手册发给它，逐项对照检查；PCB 各层导出成 PDF 或截图，让它做评审，给出 EFT、ESD 这类抗干扰的优化建议；BOM、测试报告、评审 PPT 直接交给它做。记得说明要可编辑的文件。

附件是 EtherCAT 部分的原理图 PDF 和 LAN9252 数据手册。请对照手册检查外围电路：晶振和负载电容、PHY 的偏置电阻、网络变压器接法、EEPROM、复位和配置引脚的上下拉。逐项写出原理图里的值、手册推荐值和是否符合，不符合的注明手册页码。请交付可编辑的 Excel 文件。

附件是 EtherCAT 从站板 PCB 各层导出的 PDF 和原理图，这块板要过 EFT ±2kV 测试。请从电源入口防护、网口防护、地平面、去耦电容和差分走线几方面做评审，列出问题和修改建议，按影响大小排序，每条说明依据。

附件是从 Allegro / KiCad 导出的 BOM。请整理成可编辑的 Excel：合并相同料号，按器件类型分页，补上封装和官方手册链接，查不到的标「待确认」。

5. 图片

出产品图、示意图，也能改照片。给参考图时，说清哪些保留、哪些要改。

把附件里电路板照片的背景换成纯白，去掉桌面上的杂物。板子上的器件、丝印、颜色和拍摄角度都保持不变，用在产品手册里。

参考附件的电路板照片，生成一张产品手册用的写实渲染图，正上方俯视，纯白背景，柔和的棚拍光。板子外形、安装孔、每个接口的数量和位置都要和照片一致，不要卡通化，不要加文字标注。

在哪儿用：聊天、工作还是 Codex

平时用「聊天」和 Codex 就够了。区别在于它能不能碰你电脑里的东西。

  • 聊天 问手册、查器件、聊方案、出图。手头有 PDF、截图或照片，点输入框左边的「+」发给它。
  • 工作 写测试报告、整理 BOM、出选型对比。
  • Codex 读整个固件工程、改代码、编译、跑脚本。

「工作」和 Codex 选在「此计算机」运行时，能直接读写你选中的文件夹（见第五节）；它还能自己打开浏览器去 TI 官网下载手册，或在本机跑编译看报错。

选模型

推理强度是让它想多深，越高越慢，也越费用量。

五、怎样交代任务（提示词）

什么是提示词

提示词就是你在输入框里写给 AI 的话。它不是什么口令或特殊格式，就是一份任务说明。

AI 不认识你们的板子、工程和习惯，它能参考的只有你写下的话和发给它的文件。你说得越清楚，它交回来的东西就越对。简单问题一句话就够；复杂的活，按下面的顺序交代。

怎么写：按四步交代

  1. 先讲背景这是什么项目、用的什么芯片，文件夹或附件里有什么，现在做到哪一步了。
    例：这是 EtherCAT 从站的固件工程，主控 F28379D，ESC 是 LAN9252，src 里是应用代码，ssc 里是 SSC 生成的协议栈，docs 里有 LAN9252 手册。
  2. 再讲目的和任务你最终想解决什么，这一次让它做什么。
    例：主站能扫到从站，但切不到 OP，想先找到原因。这次只分析，不改代码。
  3. 然后讲要求参考哪些资料、哪些地方不能动、结论要不要注明出处、拿不准的怎么处理。
    例：结论要对应到代码行号或手册页码；拿不准的单独列出来，不要猜。
  4. 最后讲交付物要它交回什么、什么格式。
    例：按可能性排序的原因清单，每条写上怎么验证。

不用每次都写满四项，但背景和任务最好别省。可以复制下面的模板，填空就行：

背景：这是＿＿项目，用的芯片是＿＿，文件夹（或附件）里有＿＿。目前＿＿。 任务：我想＿＿，这次请你＿＿。 要求：参考＿＿；不要改动＿＿；结论注明出处，拿不准的单独列出来。 交付：请给我＿＿（比如原因清单、可编辑的 Excel、改好的代码和修改说明）。

结果不对的时候

一次没做好，不代表它做不了。按下面的顺序处理，大多能改好：

  1. 先自查目标说清楚没有？手册、代码、日志、原理图这些材料给全没有？缺了就补上。
  2. 具体指出哪里不对在同一个对话里接着说，别只回一句「不对，重做」。
    例：第 3 条结论手册里找不到，给出页码。／只改 PWM 初始化，别动其他文件。
  3. 让它自己核对要求它对照手册再查一遍，或者编译、跑一遍看结果。
    例：请对照手册逐个核对表里的寄存器地址，对不上的标出来。
  4. 还不行就换个思路来回改几轮还偏，就新开一个对话，把材料和已经确认的结论带过去，换个说法重新交代，或者换用 GPT-6.2 Astra。

几个使用习惯

一个对话一件事
上下文就是 AI 当前能参考的内容：这个对话里前面聊过的话和你发的文件。无关的内容多了，容易把它带偏，也更费用量，所以换一件不相干的事就新开一个对话。模型名左边的小圆圈能看到用了多少，快满时 Codex 会自动压缩，不用管它。
一个项目一个文件夹
项目用来放长期要用的资料。在本机工作时，一个项目对应电脑上的一个文件夹，比如一个固件工程、一块板子的设计资料和手册。照下面三张图建好后，新对话选上这个项目，它就能直接读取和修改里面的文件。

不要让多个对话同时在同一个文件夹里工作。等一个对话做完，再开始另一个，避免两个对话同时修改同一个文件。
